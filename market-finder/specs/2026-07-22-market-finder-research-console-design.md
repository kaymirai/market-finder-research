# Market Finder Research Console UI Design

## Purpose

Market Finderの既存の5段階リサーチを、デスクトップ専用の「Research Console」へ再構成する。途中経過は一覧性を優先して圧縮し、現在の工程、処理中のキーワード、取得済み件数、失敗箇所を短時間で把握できるようにする。最終結果はコピー、CSV保存、未来デザイナー連携に使うため、途中工程とは分離した読みやすい出力画面にする。

## Confirmed Direction

- 採用案はC「Research Console」とする。
- モバイル対応は対象外とし、幅1280px以上のデスクトップ利用を前提とする。
- 検索候補生成、eRank、Etsy Marketplace Insights、EverBee、クロスニッチ、スコアリング、CSV列の判定ロジックは変更しない。
- 既存の5工程と順序を維持する。
  1. 条件を決めて候補を作る
  2. 候補を確認する
  3. eRankの需要結果を確認する
  4. Etsy公式の結果を確認する
  5. 調査結果と商品化候補
- 既存DOM IDを維持し、Chrome拡張との通信や現在のイベントリスナーを壊さない。
- 予備入力、CSV入力、SEO案、詳細説明は必要時に開く補助領域へ移し、主操作と同じ視覚的強度にしない。

## Information Architecture

### Global Header

画面上部に、現在の調査テーマ、商品種別、年、拡張機能の接続状態、進行中処理の停止操作をまとめる。調査中は現在処理している外部サービスとキーワードを1行で表示する。常時必要でない説明文は置かない。

### Five-Stage Navigation

ヘッダー直下に5工程のタブを横並びで置く。各タブは次の状態を持つ。

- `未開始`: 番号と工程名のみ
- `実行可能`: 次に操作できる工程
- `進行中`: アクセント色と進捗件数
- `完了`: チェック表示と結果件数
- `要確認`: 取得失敗や不足件数を警告表示

検索結果が存在するだけで完了扱いにはしない。各工程の既存判定条件を使い、次工程へ送れる候補件数と処理状態から状態を決める。タブは任意に戻って閲覧できるが、実行条件を満たさない後続工程の主ボタンは有効化しない。

### Working Console

第2から第4工程は、次の3列を基本とする。

- 左 `Queue`: 待機中、処理中、取得済み、数値取得失敗、保留の件数とキーワード一覧
- 中央 `Workspace`: 現在工程の結果表と主操作
- 右 `Inspector`: 選択したキーワードの数値、由来、判定理由、次の送付先

左列は約220px、右列は約320pxの固定幅、中央列は残り幅を使用する。画面全体を縦に積み上げず、各列内をスクロールさせる。現在行、処理中行、失敗行は色だけに頼らずラベルでも区別する。

第1工程は条件入力を中央に置き、左列に調査履歴、右列に今回の条件要約と開始状態を表示する。条件をすべて入力してから、中央下部の「候補を自動で探す」を押す順序にする。

### Final Results Workspace

第5工程は途中工程の3列レイアウトをそのまま流用せず、最終成果物を優先する専用画面にする。

- 上部に調査テーマ、調査ラウンド、A/B/C/D件数、取得鮮度、未取得データの有無を表示する。
- 中央左に商品化候補の一覧表を広く表示する。
- 選択候補の詳細を右側に表示し、スコア、販売実績、競合、需要、由来、判定理由、商品案、SEO案を確認できるようにする。
- 「コピー」「最終結果CSV」「未来デザイナー用CSV」を上部の固定アクションバーへまとめる。
- A/Bを商品化候補、Cを追加探索候補、Dを除外候補として明確に分離する。
- クロスニッチ再探索中も既存結果を消さず、ラウンドタブと進行帯を表示する。

## Component Boundaries

### `research-console-ui.js`

表示専用の状態を扱う新しい小さなモジュールとする。検索データの正本は既存の`state`に残す。

- 5工程の表示状態を既存データから導出する。
- 現在選択中の工程、キーワード、Queueフィルターを管理する。
- 件数表示用のview modelを返す。
- localStorageへ保存するのは選択中工程と表示フィルターだけとし、検索結果を重複保存しない。

### Existing Render Functions

`renderCandidates()`、`renderErankResults()`、`renderMarketplaceInsightPlan()`、`renderResultsTable()`などの既存関数はデータ処理を維持する。出力先コンテナとマークアップをConsole向けに調整するが、スコア算出や次工程候補の選定条件は変更しない。

`renderAll()`は全工程の巨大な結果DOMを毎回構築せず、ナビゲーション件数と現在工程を優先して更新する。非表示工程は状態サマリーのみ更新し、その工程へ移動した時点で詳細を描画する。ただし、Chrome拡張からの進捗受信とstate更新は非表示中も継続する。

### Existing DOM Contracts

Chrome拡張、イベント登録、CSV出力が参照する既存IDは維持する。要素を新しいConsoleコンテナ内へ移動しても、以下を含むID名と役割を変更しない。

- 候補生成、eRank、Etsy公式、EverBee開始ボタン
- 進捗、接続状態、件数表示
- eRank、Marketplace Insights、最終結果の一覧コンテナ
- コピー、CSV保存、SEO生成ボタン

## Data Flow

1. 既存処理が`state`を更新する。
2. Consoleの工程サマリー関数が、各工程の状態と件数を導出する。
3. 上部タブと左Queueを軽量更新する。
4. 現在表示中の工程だけ詳細レンダーを実行する。
5. 行を選択すると、選択キーだけをUI状態へ保存し、右Inspectorを更新する。
6. 外部取得の応答が来た場合、選択中の行ならInspectorも更新する。別工程の応答ならタブ件数と状態だけ更新する。

画面切り替えで検索キュー、調査ラウンド、途中結果を初期化しない。新規調査の明示操作だけが既存のリセット確認フローを通る。

## Interaction Rules

- 各工程の主操作はWorkspace内に1つだけ強く表示する。
- 「次へ」ではなく、`eRankで検索数を見る`、`Etsy公式確認を自動実行`、`EverBeeで売上を確認する`のように実行内容をボタン名にする。
- ボタンが無効な場合、直下に理由と必要件数を1行で表示する。
- 行選択は詳細表示のみを行い、外部検索やデータ送信を開始しない。
- 失敗行はQueueの「数値取得失敗」から絞り込み、失敗した列と理由をInspectorに表示する。
- 長い説明、用語説明、保留一覧は初期状態で畳む。
- 進行中モーダルは重要な停止操作が必要な場合に限る。通常進捗はヘッダーとQueue内へ表示する。

## Visual System

- 白とごく薄いグレーを基調にし、文字は濃いチャコールとする。
- 主操作と進行中状態にはティール、選択状態にはブルー、警告にはアンバー、失敗には赤を限定的に使う。
- カードの多用を避け、1px境界線、表、分割ペイン、セクション背景で構造を示す。
- 角丸は最大8pxとする。
- ボタン、タブ、Queue行、表ヘッダーの高さを固定し、状態変化でレイアウトを動かさない。
- 文字サイズを画面幅に連動させない。
- 横幅1280px未満では3列を無理に縮小せず、Console全体を横スクロール可能にする。

## Error Handling

- `未検索`、`検索済み・数値取得失敗`、`取得中`、`取得済み`を別状態として表示する。
- eRankで一部列だけ未取得の場合、取得済み数値を残し、不足列をInspectorへ明示する。
- 外部サイト待機中はタイマー残秒よりも、待っている画面要素または数値列を表示する。
- タイムアウト後も行を削除せず、再試行対象としてQueueへ残す。
- 拡張機能が未接続の場合、検索結果は維持し、接続操作だけをヘッダーに表示する。
- 0件と未取得を同じ表示にしない。

## Performance Requirements

- 非表示工程の長い一覧DOMを毎回再生成しない。
- 1回の外部取得イベントで全面再描画せず、工程サマリー、対象行、Inspectorを優先更新する。
- 既存の検索待機、タイムアウト、再試行ロジックは本UI変更では変更しない。
- 500件規模のeRank結果がある状態でも、工程切り替えと行選択が体感上すぐ反応することを確認する。

## Testing

### Automated

- 5工程の状態導出を純粋関数としてテストする。
- active stageとQueueフィルターの保存・復元をテストする。
- 既存IDがHTMLに残り、各主要ボタンが1要素だけ存在することをテストする。
- 0件、未取得、一部取得失敗、完了の表示をテストする。
- 既存の候補生成、eRank query plan、Marketplace Insights、EverBee、クロスニッチ、スコアリングの回帰テストを実行する。

### Desktop Verification

- 1440x900と1920x1080で、ヘッダー、5タブ、3列Console、最終結果画面を確認する。
- 表、Queue、Inspectorが互いに重ならず、各領域内でスクロールできることを確認する。
- eRank取得中に別工程へ移動し、戻った時にキューと結果が維持されることを確認する。
- 第5工程でコピー、通常CSV、未来デザイナー用CSVが従来どおり出力されることを確認する。

## Out of Scope

- モバイルおよびタブレット向け最適化
- スコア式、競合区分、候補生成、クロスニッチ生成の変更
- eRank、Etsy、EverBeeの取得手順やタイムアウト値の変更
- 新しいUIフレームワークや依存パッケージの導入
- CSV列名と未来デザイナー側のデータ契約変更

## Acceptance Criteria

1. 初見で現在工程、次に行う操作、処理件数、失敗件数が1画面内で分かる。
2. 第2から第4工程では、Queue、一覧、選択語句の詳細を同時に確認できる。
3. 第5工程では途中経過に邪魔されず、候補比較、コピー、CSV出力を行える。
4. 工程を切り替えても検索処理と結果が消えない。
5. 無効な主ボタンには、押せない理由が必ず表示される。
6. 既存の検索、判定、Chrome拡張、CSV出力の挙動が維持される。
7. 500件規模の結果でも、非表示工程の再描画を抑えて操作遅延を改善する。
